# Аудит производительности: что сделано, где мы, что дальше

Состояние на 2026-11-23, ветка `feature/native-renderer-n3a`, последний замер — прогон `out/console-test/nak01`
(коммит 3addcea, портатив, CPU 1020 / GPU 460.8 / память 1600 МГц, сцена закреплена на 768×432).

Цель: ровные 30 кадров/с в бою с запасом на тяжёлые сцены. Игра сама ограничена 30 кадрами и квантует кадр по
vblank: кадр, который не уложился в 33.3 мс, ждёт до 50 мс. Поэтому «с запасом» значит GPU ≤ ~26 мс и поток
рендера ≤ ~25 мс на кадр в обычном бою, тогда тяжёлые места (+30–40%) ещё укладываются в 33.

## 0. Аудит 2026-11-24: карта узких мест, чтобы не ходить кругами

Разделы 1–6 ниже — состояние на 2026-11-23, до трёх прогонов на консоли; этот раздел их заменяет как план.

### Бюджет

30 кадров = 33.3 мс на кадр, и укладываться должны **все три участника по отдельности и вместе**: потоки игры
(CPU), поток рендера ring (CPU), GPU. Кадр длиннее 33.3 мс игра доводит до 50 мс (20 кадров) — поэтому «чуть
больше бюджета» выглядит как провал до 20. Запас: каждый участник ≤ ~26 мс, и ring с GPU должны работать
параллельно, а не по очереди.

**Урок:** ускорение кода игры на Маке не переносится на консоль. На A57 главная функция потока игры
`sub_825C3C20` (32% его времени) — обход связного списка объектов сцены с отсечением: процессор стоит на загрузке
следующего узла и данных узла (промахи кэша/TLB), а не на арифметике. Проверять только на консоли, по мс потоков.

### Узкие места по порядку вклада

1. **Ring и GPU работают по очереди из-за зеркала (деревня).** Игра каждый кадр переписывает на месте часть
   вершин/индексов. Зеркало памяти одно, и перед перезаписью области, которую ещё читает отправленный кадр,
   ring ждёт GPU (`MirrorSync` → `wait_submission` → `WaitFor`). Это ≈1 ожидание на кадр: ring не может готовить
   кадр N+1, пока GPU рисует кадр N. Цена: 10–18 мс простоя ring на кадр плюс потерянное наложение ring и GPU.
   **Решение:** не ждать, а «переименовывать» — менявшийся диапазон, который ещё читает GPU, копировать в
   потоковую область того же буфера зеркала (кольцевой буфер, освобождается по забору отправки) и для отрисовок
   этого кадра брать адрес оттуда: сдвиг в fetch-константах вершин (они и так собираются на каждую отрисовку) и
   смещение в `vkCmdBindIndexBuffer`. Ожидание: ожидания зеркала → 0, ring −10…−18 мс/кадр в таких сценах.
2. **Поток игры ~33 мс/кадр (деревня).** Треть — `sub_825C3C20` (обход списка, упор в память). Гипотезы:
   - **TLB:** окно гостевой памяти отображено страницами 4 КБ (`guest pages: mode 0, window base mod 2MB 0x61000`,
     `2MB-aligned starts 0`). В SDK есть готовый режим `guest_memory_large_pages = 1/2` (окно выровнено, ядро
     может ставить блоки 2 МБ) и замер `guest_memory_tlb_benchmark`. Никогда не включали.
   - **Вытеснение:** ring имеет приоритет 0x2C, потоки игры 0x3B, у всех маска ядер 0–2. Когда ring и поток
     игры на одном ядре, игра стоит. В SDK есть закрепление главного потока игры за отдельным ядром
     (`RexSwitchPerfExclusiveCore`), в NieR не подключено.
   - Ещё один поток игры (`XThread…` с кодом 0x824F…–0x8250…, похоже CRI-звук/файлы) берёт ~35% ядра.
3. **Собственная цена ring помимо ожиданий:** XXH3-хэширование зеркала и текстур (20% ring, ~250 МБ/с — области до
   2 МБ перехэшируются на каждом использовании, см. native-n3a-rulings), копии (6%), `std::map`/выделения памяти
   (~8%), драйвер NVK (~10%). Рычаги C1–C2 из раздела 5.
4. **GPU в сценах с эффектами (31–36 мс).** Рычаги G1–G6 из раздела 5; карта теней в полном размере стоит 5–7 мс.

### Не ходить кругами

- Мерить на консоли и по мс на кадр каждого участника (поток игры, ring: отрисовки/зеркало/ожидание GPU, GPU),
  плюс «ожидания зеркала на отправку». Число кадров само по себе не говорит, кто держит.
- Мак годится для проверки корректности, но не для оценки выигрыша CPU.
- Одна правка на прогон, одно и то же место (сохранение в деревне) + по возможности бой с эффектами.

### Порядок опытов и правило решения

| # | Опыт | Цена | Ожидание | Оставляем, если |
|---|---|---|---|---|
| 1 | `guest_memory_large_pages = 1` + `guest_memory_tlb_benchmark = 64` (только настройки) | минуты | поток игры −10…−30%, число из замера TLB | мс потока игры на кадр заметно меньше; затем попробовать режим 2 |
| 2 | Переименование диапазонов зеркала вместо ожидания GPU | средняя правка | ожидания зеркала → 0, ring −10…−18 мс в деревне | ожиданий нет, картинка без артефактов |
| 3 | Отдельное ядро для потока игры (закрепление из SDK по cvar) | маленькая правка | меньше вытеснения | мс потока игры меньше при той же нагрузке |
| 4 | Ring: меньше хэширования и выделений (C1, C2) | средняя | ring −3…−6 мс | — |
| 5 | GPU для эффектов: G1 → G2…G6 | разная | GPU −5…−10 мс в тяжёлых сценах | — |

После 1–3 ожидаем деревню около 25–30 кадров; 4–5 — запас и сцены с эффектами.

### Результаты опытов

- **Опыт 1 (village_lp01, конфиг):** замер TLB на консоли — случайная загрузка по 64 МБ: страницы 4 КБ 219 нс,
  64 КБ 162 нс, блоки 2 МБ 158 нс (по 8 МБ: 181 / 160 / 156). Режим 1 включился (окно на границе 2 МБ). Поток
  игры в деревне 52–64% при 20–26 кадрах, ~25–30 мс/кадр против 30–33 мс — лучше, но кадров всё ещё ~20: ring
  по-прежнему ждёт зеркало ~1 раз на кадр (184–257 ожиданий за 10 с, 3.3–3.6 с простоя). Пользователь: «смотрю в
  пол — 30». `guest_memory_large_pages = 1` теперь в `app/nier_switch.toml`. Сбои в отчёте того прогона — модуль
  `gtav` (соседний порт), не NieR.
- **Опыт 2 (зеркало без ожиданий, 35f3a41):** менявшийся диапазон, который ещё читает отправленный кадр, больше
  не ждёт GPU: байты кладутся во временный буфер текущей отправки, а в зеркало их копирует сам GPU
  (`vkCmdCopyBuffer` в командном буфере загрузки, барьер ALL→TRANSFER перед первой копией в отправке). Ключ,
  обновивший содержимое при незавершённых читателях, держит их «обязательными» для перекрывающих ключей (ac720a2).
  Включается только для когерентной памяти зеркала (тип пишется в лог `guest mirror:`), выключается
  `nier_mirror_staging = false`. Мак, деревня: 0 ожиданий, ~1200 копий через GPU за 10 с, картинка та же.
  **Консоль (village_stage01):** ожиданий зеркала 0, зеркало uncached coherent (тип 1). Где людей мало — 28–29
  кадров, в толпе (430–500 отрисовок на кадр) — 20–25. ring ~27–30 мс/кадр (из них зеркало 8–9 мс: за 10 с
  хэшируется ~2.6 ГБ зеркала и ~1.3 ГБ текстур, XXH3 ~20% сэмплов ring), поток игры ~32 мс/кадр, GPU 23–25 мс.
  Теперь в толпе держат **оба потока CPU** — ring и поток игры, оба у края бюджета. Пользователь: «стало лучше,
  но в деревне, где много людей, всё равно 20».
- **Хэширование (adaea39):** маленькие текстуры, стабильные 8 проверок подряд, перехэшируются раз в 4 кадра, как
  большие (Мак, деревня: хэш текстур −28%). Проверку маленьких диапазонов зеркала раз в кадр отвергли: экономия ~3%,
  а диапазон, который после долгой стабильности игра начнёт переписывать между отрисовками внутри кадра, пропускался
  бы навсегда (проверка всегда попадает в одну фазу).

### Исследование агентами (2026-11-24)

- **Другие порты на ReXGlue** (nfsmw-nx и masseffect-nx — та же архитектура PM4→Vulkan/NVK; Lazarus/ME2, sa2-nx,
  SHH, Naruto — на deko3d): переименование загрузок по слотам кадров (у них −207 мс простоя), «store cards»
  (генератор помечает 4-КБ страницу при записи гостя — хэширование ring 16% → 0% в sa2-nx), патчи mesa-switch
  nfsmw-nx (дельты дескрипторов, константные буферы), `fp_moves_modeless` (сэмплы после `msr fpcr`), отсечение
  игрой по запросам окклюзии (у ME2 16 → 27 fps; NieR запросов окклюзии не делает — 0 событий за 10 с),
  жёсткое закрепление потоков за ядрами у других ухудшало минимум fps — опыт 3 снят. Четвёртое ядро даёт только
  запуск через NSP-форвардер — решение пользователя.
- **Горячая функция потока игры `sub_825C3C20`** — не отсечение видимости, а широкая фаза коллизий: лучевые
  запросы по пространственному хэшу (контроллер персонажа, лучи к земле), 5–9 мс/кадр. Рендерные настройки на
  неё не влияют. Нативная замена с упреждающей загрузкой — оценка −3…−5 мс. Поток на ~35% — звук CRI
  (ревербератор ~29%, декодер ADX ~10%), настоящая работа.
- **Ring помимо ожиданий** (~28 мс CPU/кадр): хэш текстур (−0.6…−1.2 мс), запоминание `Textures::View`
  (−0.6…−1.0), выделения памяти в `PixelModule` и др. (−0.3…−0.5), дескрипторы и константы (−0.5…−1.0),
  загрузки шейдеров (−0.3…−0.5), константы PM4 напрямую (−0.2…−0.4), таймеры (−0.15…−0.3) — всего −4…−7 мс.
  Найдена ошибка: резолв глубины привязывал свой пайплайн, а кэш `bound_pipeline_` не сбрасывался — следующая
  отрисовка могла пропустить привязку (исправлено в 0e4aea4 вместе с пределом трассы в 3000 кадров).

## 3. Что проверено и закрыто — не возвращаться

- **Транслятор шейдеров больше не главная беда.** По статистике NAK (nak01): ни в одном PS нет спиллов и
  локальной памяти, занятость 48–64 warp/SM, инструкций умеренно (маска теней 241, карта теней 33). Если бы
  пиксели закрашивались по разу, маска стоила бы ~0.5 мс, карта ~0.3 мс; на деле 4–8 и 3–5. Цена — в числе
  фрагментов (перерисовка, поздний Z), а не в коде шейдера.
- **«Сцена 1x» (MSAA 4x → 1x)** — в бою 4x-поверхности не в топе (measure01).
- **Режимы exact math / explicit gradients** — разница была от перекомпиляции при переключении, не от цены.
- **RGBA8-копия глубины** (режим no raw depth) — 0 эффекта (lap05).
- **A/B по fps в бою** не различает CPU-правки: сцена слишком гуляет. Сравнивать только по мс проходов и шейдеров.
- **Патч конфиг-блока разрешения `sub_82496830`** ломает текст и камеру.
- **Карта теней без `oDepth`** (G2) — нельзя: `c0.x = 0.0115`, проекция света перспективная, игра пишет в карту
  линейную глубину `z·k`, а растеризатор даёт `z/w`.
- **Уровень разрешения 3** — игра принимает только 0–2 (`sub_82591720`), под каждый уровень заранее создаёт
  поверхности; меньший размер — только через множитель уровня 2 (сделано, 88f1956).
- **Потолок самой игры** — 30 кадров; режимы no draws / quarter screen дают 28–29, а не 30, из-за CPU.

## 4. Статтеры при первой встрече шейдера

Что происходит. Новый шейдер (или новая комбинация состояния) на первой отрисовке проходит трансляцию Xenos →
SPIR-V (до ~3 мс), специализацию и компиляцию NAK внутри `vkCreateGraphicsPipelines` прямо в потоке рендера.
Компиляция NAK на ядре A57 1 ГГц — десятки мс на крупный шейдер; за прогон создаётся ~230 пайплайнов. Пока
компилируется, кадр стоит.

Что есть сейчас. В порте Mesa включён дисковый кэш шейдеров (`-Dshader-cache=true`, один файл в
`sdmc:/.mesa`). Повторная встреча того же шейдера должна идти из кэша, но:
- не проверено, что файл кэша вообще пишется и переживает закрытие игры через HOME (запись может откладываться
  до чистого выхода);
- диагностическая сборка 61f731a с `nier_shader_assembly_file` захватывает ассемблер: Mesa для таких пайплайнов
  обходит кэш, и каждый шейдер ещё и пишется на карту — статтеры в ней хуже обычного;
- время компиляции пайплайна мы не меряем.

Что делать, по порядку:
1. Выключить захват ассемблера в обычной сборке (оставить только по cvar для диагностики).
2. Мерить время создания каждого пайплайна (мс, максимум за 10 с) — видно, сколько стоит статтер.
3. Свой постоянный `VkPipelineCache`: загрузка из `sdmc:/switch/nier-nx/pipelines.bin` при старте, сохранение
   на карту после новых пайплайнов (раз в несколько секунд и на загрузочных экранах), а не только при выходе.
   Не зависит от поведения кэша Mesa.
4. Прогрев: список ключей пайплайнов (хэши шейдеров, состояние, значения специализации) пишется на карту; при
   старте и на загрузках пайплайны создаются заранее, в фоновом потоке. Со списком из одной полной игры
   статтеры уходят почти полностью и при первом заходе в локацию после переустановки.
5. Запасной вариант на совсем новый шейдер — асинхронная компиляция с пропуском отрисовки на пару кадров
   (короткий «недорисованный» объект вместо фриза). Только если 3–4 не хватит: даёт видимые артефакты.

## 5. Рычаги производительности

Оценки выигрыша — по замерам nak01; «без потери картинки» значит результат пиксель в пиксель тот же.

### GPU без потери картинки

| # | Что | Выигрыш | Риск / проверка |
|---|---|---|---|
| G1 | **Счётчик фрагментов по проходам** (pipeline statistics, FRAGMENT_SHADER_INVOCATIONS) | диагностика | обязателен перед G2–G4: покажет перерисовку каждого прохода |
| G2 | **Карта теней без `oDepth`.** VS пишет в интерполятор ту же позицию, что в `oPos`, PS пишет `oDepth = saturate(z * c0.x)`. Если `c0.x = 1` и проекция ортогональная, это ровно глубина растеризатора; запись из шейдера только выключает ранний Z. Специализация убирает запись глубины, когда условие выполнено | 2–3 мс | проверить `c0.x` и строку `w` проекции на Маке; если не равны — не трогать |
| G3 | **Маска теней:** `kill` по границе каскада + поздний Z, геометрия рисуется заново. По G1 решить: ранние тесты для этих PS (допустимо, если отбрасывание только по границе каскада) | 2–4 мс | средний: нужно разобрать состояние глубины прохода |
| G4 | **Повторные резолвы:** ~7 за кадр одного и того же `c 10E` в одни адреса, часть без отрисовок между ними | ~0.5–1 мс | низкий: пропуск, только если источник и приёмник не менялись |
| G5 | **Барьеры:** `FullBarrier` (ALL→ALL, ожидание простоя GPU) на каждом резолве и смене цели, десятки за кадр | 0.5–1.5 мс | средний: точечные барьеры по реальным зависимостям |
| G6 | **Переносы EDRAM** (depth→color compute со storage images, как был резолв глубины) | до ~1 мс | низкий: тот же приём, что в 3addcea |

Сумма G2–G6: ~6–10 мс → GPU ~25–28 мс в обычном бою.

### GPU с компромиссом в картинке (решение за тобой)

| # | Что | Выигрыш |
|---|---|---|
| V1 | Маска теней в половинном разрешении (640×360 → 320×180): тени мягче по краю | 3–4 мс |
| V2 | Карта теней 1024² → 768² или 512²: тени грубее, особенно вдали | 1.5–3 мс |
| V3 | Композит и HUD не в 1280×720, а ближе к разрешению сцены | ~1 мс, HUD мыльнее |
| V4 | Док-режим (GPU 768 МГц штатно, +67%) или разгон через sys-clk — меняет настройки консоли | GPU-упор почти исчезает |

### Поток рендера (CPU)

| # | Что | Выигрыш |
|---|---|---|
| C1 | Зеркало памяти 4–7 мс/кадр: хэширование диапазонов вершин/индексов на каждой отрисовке → отслеживание записи по страницам или реже проверять стабильные диапазоны | 2–4 мс |
| C2 | Стоимость отрисовки 60–105 мкс: остаток после 32ed25c — упаковка констант, поиск пайплайна, NVK `vk_dynamic_graphics_state_copy`; профиль семплами (`deploy.sh --stacks`) | 3–6 мс |
| C3 | Вывод 2–3.4 мс/кадр на CPU — разобрать по семплам | 1–2 мс |
| C4 | Привязка потоков к ядрам (ring на своём ядре) — меньше вытеснения потоков игры | замер |

Цель по ring: ≤ 20 мс/кадр в обычном бою, тогда тяжёлые сцены (×1.4) укладываются.

## 6. Порядок работы

Каждый шаг — один прогон на консоли, сравнение по мс проходов, а не по fps.

1. **Статтеры:** выключить захват ассемблера, мерить время создания пайплайнов, свой постоянный кэш
   пайплайнов + прогрев по списку. Сразу видно игроку.
2. **Диагностика теней:** счётчик фрагментов (G1) + проверка `c0.x`/проекции на Маке.
3. **Тени без потери картинки:** G2, затем G3 по данным G1.
4. **Резолвы и барьеры:** G4, G5, G6.
5. **Ring CPU:** семплы и C1–C3.
6. **Компромиссы V1–V4** — только если после 1–5 запаса не хватает, и по твоему выбору.

Ожидание без потери картинки: GPU 30–36 → ~25–28 мс, ring 22–30 → ~18–22 мс, то есть 30 кадров в обычном
бою и заметно меньше провалов в тяжёлых местах. Полный запас на самые тяжёлые сцены, скорее всего, потребует
одного из V1/V2 или док-режима.
