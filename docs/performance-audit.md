# Аудит производительности: что сделано, где мы, что дальше

Состояние на 2026-11-23, ветка `feature/native-renderer-n3a`, последний замер — прогон `out/console-test/nak01`
(коммит 3addcea, портатив, CPU 1020 / GPU 460.8 / память 1600 МГц, сцена закреплена на 768×432).

Цель: ровные 30 кадров/с в бою с запасом на тяжёлые сцены. Игра сама ограничена 30 кадрами и квантует кадр по
vblank: кадр, который не уложился в 33.3 мс, ждёт до 50 мс. Поэтому «с запасом» значит GPU ≤ ~26 мс и поток
рендера ≤ ~25 мс на кадр в обычном бою, тогда тяжёлые места (+30–40%) ещё укладываются в 33.

## 1. Где мы сейчас

Бой: 25–29 кадров/с, тяжёлые места 13–23. Упор двойной — GPU и поток рендера (ring) на CPU.

## 3. Что проверено и закрыто — не возвращаться

- **Транслятор шейдеров больше не главная беда.** По статистике NAK (nak01): ни в одном PS нет спиллов и
  локальной памяти, занятость 48–64 warp/SM, инструкций умеренно (маска теней 241, карта теней 33). Если бы
  пиксели закрашивались по разу, маска стоила бы ~0.5 мс, карта ~0.3 мс; на деле 4–8 и 3–5. Цена — в числе
  фрагментов (перерисовка, поздний Z), а не в коде шейдера.
- **«Сцена 1x» (MSAA 4x → 1x)** — в бою 4x-поверхности не в топе (measure01).
- **Режимы exact math / explicit gradients** — разница была от перекомпиляции при переключении, не от цены.
- **RGBA8-копия глубины** (режим no raw depth) — 0 эффекта (lap05).
- **A/B по fps в бою** не различает CPU-правки: сцена слишком гуляет. Сравнивать только по мс проходов и шейдеров.
- **Патч конфиг-блока разрешения `sub_82496830`** ломает текст и камеру.
- **Карта теней без `oDepth`** (G2) — нельзя: `c0.x = 0.0115`, проекция света перспективная, игра пишет в карту
  линейную глубину `z·k`, а растеризатор даёт `z/w`.
- **Уровень разрешения 3** — игра принимает только 0–2 (`sub_82591720`), под каждый уровень заранее создаёт
  поверхности; меньший размер — только через множитель уровня 2 (сделано, 88f1956).
- **Потолок самой игры** — 30 кадров; режимы no draws / quarter screen дают 28–29, а не 30, из-за CPU.

## 4. Статтеры при первой встрече шейдера

Что происходит. Новый шейдер (или новая комбинация состояния) на первой отрисовке проходит трансляцию Xenos →
SPIR-V (до ~3 мс), специализацию и компиляцию NAK внутри `vkCreateGraphicsPipelines` прямо в потоке рендера.
Компиляция NAK на ядре A57 1 ГГц — десятки мс на крупный шейдер; за прогон создаётся ~230 пайплайнов. Пока
компилируется, кадр стоит.

Что есть сейчас. В порте Mesa включён дисковый кэш шейдеров (`-Dshader-cache=true`, один файл в
`sdmc:/.mesa`). Повторная встреча того же шейдера должна идти из кэша, но:
- не проверено, что файл кэша вообще пишется и переживает закрытие игры через HOME (запись может откладываться
  до чистого выхода);
- диагностическая сборка 61f731a с `nier_shader_assembly_file` захватывает ассемблер: Mesa для таких пайплайнов
  обходит кэш, и каждый шейдер ещё и пишется на карту — статтеры в ней хуже обычного;
- время компиляции пайплайна мы не меряем.

Что делать, по порядку:
1. Выключить захват ассемблера в обычной сборке (оставить только по cvar для диагностики).
2. Мерить время создания каждого пайплайна (мс, максимум за 10 с) — видно, сколько стоит статтер.
3. Свой постоянный `VkPipelineCache`: загрузка из `sdmc:/switch/nier-nx/pipelines.bin` при старте, сохранение
   на карту после новых пайплайнов (раз в несколько секунд и на загрузочных экранах), а не только при выходе.
   Не зависит от поведения кэша Mesa.
4. Прогрев: список ключей пайплайнов (хэши шейдеров, состояние, значения специализации) пишется на карту; при
   старте и на загрузках пайплайны создаются заранее, в фоновом потоке. Со списком из одной полной игры
   статтеры уходят почти полностью и при первом заходе в локацию после переустановки.
5. Запасной вариант на совсем новый шейдер — асинхронная компиляция с пропуском отрисовки на пару кадров
   (короткий «недорисованный» объект вместо фриза). Только если 3–4 не хватит: даёт видимые артефакты.

## 5. Рычаги производительности

Оценки выигрыша — по замерам nak01; «без потери картинки» значит результат пиксель в пиксель тот же.

### GPU без потери картинки

| # | Что | Выигрыш | Риск / проверка |
|---|---|---|---|
| G1 | **Счётчик фрагментов по проходам** (pipeline statistics, FRAGMENT_SHADER_INVOCATIONS) | диагностика | обязателен перед G2–G4: покажет перерисовку каждого прохода |
| G2 | **Карта теней без `oDepth`.** VS пишет в интерполятор ту же позицию, что в `oPos`, PS пишет `oDepth = saturate(z * c0.x)`. Если `c0.x = 1` и проекция ортогональная, это ровно глубина растеризатора; запись из шейдера только выключает ранний Z. Специализация убирает запись глубины, когда условие выполнено | 2–3 мс | проверить `c0.x` и строку `w` проекции на Маке; если не равны — не трогать |
| G3 | **Маска теней:** `kill` по границе каскада + поздний Z, геометрия рисуется заново. По G1 решить: ранние тесты для этих PS (допустимо, если отбрасывание только по границе каскада) | 2–4 мс | средний: нужно разобрать состояние глубины прохода |
| G4 | **Повторные резолвы:** ~7 за кадр одного и того же `c 10E` в одни адреса, часть без отрисовок между ними | ~0.5–1 мс | низкий: пропуск, только если источник и приёмник не менялись |
| G5 | **Барьеры:** `FullBarrier` (ALL→ALL, ожидание простоя GPU) на каждом резолве и смене цели, десятки за кадр | 0.5–1.5 мс | средний: точечные барьеры по реальным зависимостям |
| G6 | **Переносы EDRAM** (depth→color compute со storage images, как был резолв глубины) | до ~1 мс | низкий: тот же приём, что в 3addcea |

Сумма G2–G6: ~6–10 мс → GPU ~25–28 мс в обычном бою.

### GPU с компромиссом в картинке (решение за тобой)

| # | Что | Выигрыш |
|---|---|---|
| V1 | Маска теней в половинном разрешении (640×360 → 320×180): тени мягче по краю | 3–4 мс |
| V2 | Карта теней 1024² → 768² или 512²: тени грубее, особенно вдали | 1.5–3 мс |
| V3 | Композит и HUD не в 1280×720, а ближе к разрешению сцены | ~1 мс, HUD мыльнее |
| V4 | Док-режим (GPU 768 МГц штатно, +67%) или разгон через sys-clk — меняет настройки консоли | GPU-упор почти исчезает |

### Поток рендера (CPU)

| # | Что | Выигрыш |
|---|---|---|
| C1 | Зеркало памяти 4–7 мс/кадр: хэширование диапазонов вершин/индексов на каждой отрисовке → отслеживание записи по страницам или реже проверять стабильные диапазоны | 2–4 мс |
| C2 | Стоимость отрисовки 60–105 мкс: остаток после 32ed25c — упаковка констант, поиск пайплайна, NVK `vk_dynamic_graphics_state_copy`; профиль семплами (`deploy.sh --stacks`) | 3–6 мс |
| C3 | Вывод 2–3.4 мс/кадр на CPU — разобрать по семплам | 1–2 мс |
| C4 | Привязка потоков к ядрам (ring на своём ядре) — меньше вытеснения потоков игры | замер |

Цель по ring: ≤ 20 мс/кадр в обычном бою, тогда тяжёлые сцены (×1.4) укладываются.

## 6. Порядок работы

Каждый шаг — один прогон на консоли, сравнение по мс проходов, а не по fps.

1. **Статтеры:** выключить захват ассемблера, мерить время создания пайплайнов, свой постоянный кэш
   пайплайнов + прогрев по списку. Сразу видно игроку.
2. **Диагностика теней:** счётчик фрагментов (G1) + проверка `c0.x`/проекции на Маке.
3. **Тени без потери картинки:** G2, затем G3 по данным G1.
4. **Резолвы и барьеры:** G4, G5, G6.
5. **Ring CPU:** семплы и C1–C3.
6. **Компромиссы V1–V4** — только если после 1–5 запаса не хватает, и по твоему выбору.

Ожидание без потери картинки: GPU 30–36 → ~25–28 мс, ring 22–30 → ~18–22 мс, то есть 30 кадров в обычном
бою и заметно меньше провалов в тяжёлых местах. Полный запас на самые тяжёлые сцены, скорее всего, потребует
одного из V1/V2 или док-режима.
