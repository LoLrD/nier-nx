# Нативный рендерер NieR — дизайн

Дата: 2026-11-17. Продолжает `2026-11-17-nier-nx-port-design.md` (цель — играть на Switch, 30 FPS на стоковых частотах
или минимальном разгоне, качество графики жертвуется).

## Зачем

Порт рисует через общую эмуляцию видеочипа Xbox 360 из SDK (Xenos-плагин, путь Xenia). После всех правок фазы
производительности (журнал `docs/bringup-log.md`) на Switch при стоковых частотах (CPU 1020, GPU 460.8, память 1600 МГц):

| | было | сейчас |
|---|---|---|
| меню | 6.3 FPS | 41 FPS |
| геймплей пролога | 1.4 FPS | ~6 FPS, кадр ~150 мс |

Геймплей упирается в видеочип. По A/B-кругу: закраска пикселей ~55 мс, копирования экрана в текстуры ~29 мс, повторная
загрузка текстур ~27 мс, переносы между буферами EDRAM ~21 мс, вершины ~12 мс. Без работы видеочипа кадр 35 мс
(процессорная стоимость эмуляции). Большая часть этого — цена самой эмуляции: результат каждого копирования экрана
идёт через память игры и потом заново грузится как текстура, буферы EDRAM гоняются между форматами, вершины и текстуры
читаются через зеркало всей памяти игры со слежкой за страницами.

Все быстрые порты Xbox 360 (Mass Effect на Switch ~25 FPS, Sonic Unleashed, Blue Dragon) пришли к своему рендереру,
который читает поток команд игры и рисует напрямую через Vulkan. Пользователь выбрал этот путь.

## Цели

1. Нативный рендерер рисует NieR правильно на macOS и Switch: титул, меню, пролог, затем вся игра.
2. 30 FPS в геймплее на Switch на стоковых частотах или минимальном разгоне; разрешение и эффекты можно урезать.
3. Основная отладка — на Маке, без участия пользователя; консоль — только для замеров скорости.

## Не цели

- Ускорять дальше Xenos-путь: он остаётся эталоном картинки и запасным вариантом.
- Брат вместо отца, русский текст, NSP-упаковка — свои этапы.
- Общий рендерер для любых игр: код под NieR, общие части — по ходу.

## Анти-цели

- Пропавшие объекты, неверная экспозиция, мерцание, которые мешают играть, — провал, даже если FPS вырос.
- Вылеты и зависания, которых нет на Xenos-пути.
- Отладка правильности картинки, требующая каждый раз рук пользователя на консоли.

## Ограничения

- База: ReXGlue SDK (вендорный форк masseffect-nx), Mesa NVK/NAK на Horizon, devkitA64 в Docker, MoltenVK на Маке.
- Код masseffect-nx — GPLv3: переносится с указанием источника в `THIRD_PARTY_NOTICES`; репозиторий личный.
- Игровые данные, извлечённые шейдеры и собранная библиотека шейдеров не коммитятся (`tools/check_repo_clean.py`);
  библиотека собирается локально из диска пользователя.
- Правила проекта: без комментариев в коде, TDD для логики, коммиты атомарные, однострочные.
- Процесс получает 3 ядра; приоритеты потоков Horizon (только 0x3B делится по времени).

## Подходы

| | Суть | Плюсы | Минусы |
|---|---|---|---|
| A | взять рендерер masseffect-nx (~50 тыс. строк) целиком и переделать | быстрее всего до первой картинки, обкатан на этом GPU | заточен под UE3 (форматы 7e3, 2x MSAA), собирается только для Switch — вся отладка на консоли |
| **B (выбран)** | свой рендерер под NieR из общих частей masseffect-nx и SDK | отладка на Маке, код под кадр NieR, понятная база | дольше до первого кадра |
| C | постепенно переделывать Xenos-путь SDK | всегда рабочее состояние | архитектура Xenia мешает главным изменениям, низкий потолок |

Потолок скорости у A и B одинаков (одни и те же приёмы); B выбран ради цикла отладки на Маке и кода под NieR.

## Решения

1. **Подключение.** Приложение создаёт свою графическую систему (`IGraphicsSystem`) в `OnPreSetup`, как masseffect-nx;
   SDK тогда не загружает Xenos-плагин. Выбор настройкой `nier_renderer = "xenos" | "native"`, по умолчанию `xenos`,
   пока нативный не догонит эталон на прологе. Код — `app/src/native/`, один и тот же для macOS и Switch;
   платформенные вызовы (`switch.h`, профайлер) — за тонким слоем.
2. **Поток команд.** Поток рендера читает кольцевой буфер PM4 игры (читатель masseffect-nx), ведёт зеркало регистров,
   обрабатывает VdSwap, прерывания и vblank, запись указателя чтения, WAIT_REG_MEM, события и записи в память. Эталон
   поведения — `CommandProcessor` SDK, который уже правильно ведёт NieR.
3. **Шейдеры — транслятор SDK на лету** (пересмотрено 2026-11-18 по решению пользователя). Нативный рендерер
   переводит микрокод из потока команд игры транслятором SDK (`SpirvShaderTranslator`, путь Xenia), который уже рисует
   NieR правильно; шейдеры кэшируются по хэшу микрокода и модификации, пайплайны — в дисковом кэше на SD. Причина:
   из 98 шейдеров, которые игра грузит до пролога, стандартный контейнер есть только у 27, остальные — в собственном
   формате движка Cavia; офлайн-библиотека XenosRecomp их не покрывает (`docs/bringup-log.md`). Вершинные данные для
   выборок транслятора по гостевым адресам рендерер готовит копированием нужных диапазонов перед отрисовкой, без
   слежки за страницами памяти. Инструменты N2 (извлечение контейнеров, обнаружение, покрытие, XenosRecomp) остаются
   для точечного ускорения горячих шейдеров позже.
4. **EDRAM.** Модель masseffect-nx «режим 4»: владение тайлами, переносы только при смене формата, доказательства
   полной перезаписи и перенаправленные очистки, трафарет через compute и копию в stencil-аспект (у NVK нет stencil
   export). MSAA-поверхности игры хранятся одновыборочными изображениями, где выборки — это пиксели (обобщение 2x-колонок
   masseffect-nx на 4x): сцена 640×360 4xMSAA и её чтение как 1280×720 1x — одно и то же изображение без переноса.
   Цена — шейдер пикселя выполняется на каждую выборку; рычаг качества ниже.
5. **Копирования экрана (резолвы)** остаются Vulkan-изображениями с ключом «адрес + формат» гостя; отрисовки читают их
   напрямую. В память игры копируются только маленькие резолвы (порог 256 КБ: цепочка экспозиции, которую игра считает
   на процессоре).
6. **Текстуры** — кэш masseffect-nx: детайлинг, загрузка, перепроверка по хэшу раз в несколько кадров; без слежки за
   страницами памяти.
7. **Вершины и индексы** — арена masseffect-nx: копия на отрисовку с дедупликацией.
8. **Пайплайны** — дисковый кэш на SD и прогрев по списку ключей, чтобы не было рывков при первой встрече шейдера.
9. **Разрешение и качество.** Первый рычаг — настройка «сцена без суперсэмплинга»: 4xMSAA-поверхности рисуются в 1x,
   вдвое меньше по каждой оси, и растягиваются при чтении. Масштаб остальных поверхностей (постобработка 1280×720) —
   следующий рычаг, если замеры покажут нужду. Интерфейс и текст не масштабируются.
10. **Раздельные слои.** Поток команд, состояние и учёт владения EDRAM не зависят от записи команд Vulkan: при
    неудаче на NVK остаётся возможность сменить бэкенд (deko3d, как запасной путь исходного дизайна).
11. **Частоты и цель.** Замер — на CPU 1020 / GPU 460.8 / память 1600 МГц (официальный профиль 0x92220007; сборка
    запрашивает его сама через apm). Цель — средние 30 FPS в 10-секундных окнах геймплея; разгон до пределов исходного
    дизайна засчитывается, если стока не хватает.
12. **Процессор игры** входит в N5: ожидания потока рендера игры в D3D (кольцо, ограда), горячие места кода игры,
    опции генератора. Разгон процессора — запасной рычаг.
13. **Места проверки.** Титул, меню и пролог по скриптовому маршруту (`app/input/prologue.tsv`) — для N1–N4. Для N5
    добавляется первая деревня после пролога (продление маршрута или сохранение, сделанное на Маке); сохранения
    пользователя из поздних мест — дополнительный источник, когда появятся. Вся игра проверяется прохождением
    пользователя после N5.
14. **Запуски на консоли — редкие** (2–3 за сессию, каждый требует рук пользователя). Поэтому замеры пакетные:
    A/B-круг профайлера плюс файл управления на SD (путь в `nier.toml`), который игра перечитывает на лету, а Мак
    обновляет по FTP во время запуска, — много вариантов настроек за один запуск. Удалённый запуск игры не входит.
15. **Измерения.** Время GPU по категориям (отрисовки, переносы EDRAM, резолвы, текстуры, вывод, простой) по
    таймстемпам — в профайлере с первой сборки для Switch. A/B-круг профайлера сохраняется.

## Этапы

| # | Результат | Где проверяется |
|---|---|---|
| N1 | Скелет: с `nier_renderer = "native"` игра доходит до меню с теми же таймингами, экран чёрный, без зависаний | Мак, `mac_smoke` |
| N2 | Шейдеры: каждый шейдер, который игра грузит на маршрутах титул → меню → пролог, переведён транслятором SDK в модуль Vulkan, 0 ошибок; время перевода измерено | Мак |
| N2.5 | Пробный замер на консоли: шейдеры и отрисовки сцены нативным путём, без полной правильности — проверка, что цена отрисовки на NVK и 4x на каждую выборку не стена | Switch |
| N3 | Картинка: титул, меню и пролог совпадают с эталоном Xenos (снимки на тех же точках маршрута, экспозиция, нет пропавших объектов) | Мак |
| N4 | Первый замер на консоли; промежуточная цель — ≥ 15 FPS в прологе на стоке | Switch |
| N5 | Оптимизация до 30 FPS (сток или минимальный разгон), с рычагами качества | Switch |

Каждый этап — свой план; после N3 нативный путь становится путём по умолчанию.

## Риски

- Переводчик XenosRecomp может ошибаться на шейдерах NieR (у masseffect-nx 0,2 % не собрались, были дефекты старой
  версии) — сравнение с эталоном Xenos на Маке ловит это рано.
- Версия XDK у NieR (2010) отличается от Mass Effect (2007): смещения в объектах D3D и сигнатуры функций могут не
  совпасть — поиск по сигнатурам проверяется на трассе вызовов.
- Шейдер на каждую выборку 4x может оказаться дороже, чем нативный MSAA, — рычаг из решения 9 и замер N4.
- Объём: десятки тысяч строк переноса и адаптации; риск растянуть. Этапы N1–N3 дают проверяемые точки.

## Остаётся строителю

Порядок переноса файлов, внутренние интерфейсы между компонентами, формат режимов обнаружения и отчётов, имена
настроек (кроме `nier_renderer`), инструменты сравнения снимков с эталоном, разбиение этапов на задачи.
